# 08 KV 缓存显存分配

## 本课目标

- 亲手算出"一个块 28 MiB"这个数；
- 看懂 `num_kvcache_blocks` 那个公式里 `used - peak + current` 的含义；
- 知道 warmup 为什么必须在分配之前、为什么它跑的是一个"假 prefill"；
- 理解"按模块顺序注入 k_cache/v_cache"这个隐式契约的风险。

## 1. 一个块占多少字节

```python
# model_runner.py:110-112
num_kv_heads = hf_config.num_key_value_heads // self.world_size
head_dim = getattr(hf_config, "head_dim", hf_config.hidden_size // hf_config.num_attention_heads)
block_bytes = 2 * hf_config.num_hidden_layers * self.block_size * num_kv_heads * head_dim * hf_config.dtype.itemsize
```

五项乘起来：

| 因子 | 含义 | Qwen3-0.6B |
| --- | --- | ---: |
| `2` | K 和 V 各一份 | 2 |
| `num_hidden_layers` | 每层都有自己的 K/V | 28 |
| `block_size` | 一块装多少 token | 256 |
| `num_kv_heads // world_size` | 每张卡负责几个 KV 头 | 8 / 1 = 8 |
| `head_dim` | 每个头的维度 | 128 |
| `dtype.itemsize` | bf16 = 2 字节 | 2 |

```
2 × 28 × 256 × 8 × 128 × 2 = 29,360,128 B = 28.0 MiB / 块
```

（0.6B 的 config 实测：`num_hidden_layers=28, num_key_value_heads=8, head_dim=128, torch_dtype=bfloat16`，从 HuggingFace 的 `Qwen/Qwen3-0.6B/config.json` 读到。）

推论：**一块 = 256 token 的完整 KV**。4096 token 的序列要 16 块 = 448 MiB。所以在 8 GB 卡上（可用约 6.5 GB），KV 池上限约 230 块 ≈ 5.9 万 token 总量 —— 这就是"小模型 + 短上下文"场景的物理边界。

TP 的收益也在这里：`num_kv_heads // world_size`，**卡越多每块越小**。TP=2 时一块 14 MiB，同样显存能装两倍的块数（总 token 容量不变，因为两份卡各存一半头）。

## 2. 块数公式

```python
# model_runner.py:106-114
free, total = torch.cuda.mem_get_info()
used = total - free
peak = torch.cuda.memory_stats()["allocated_bytes.all.peak"]
current = torch.cuda.memory_stats()["allocated_bytes.all.current"]
...
config.num_kvcache_blocks = int(total * config.gpu_memory_utilization - used - peak + current) // block_bytes
assert config.num_kvcache_blocks > 0
```

拆开看三种"占用量"：

| 量 | 是谁 | 为什么这么算 |
| --- | --- | --- |
| `used = total - free` | **整张卡**已占用（含别的进程、CUDA context、本进程） | 从上限里先扣掉 |
| `peak` | torch 分配器在本进程的**历史最高**分配 | 真正跑推理时要用到这么多 |
| `current` | torch 分配器**当前**持有（warmup 后已 empty_cache，所以 < peak） | 已经包含在 `used` 里了 |

于是：

```
可用 = total × 0.9 − used − peak + current
      └─ 目标上限 ─┘   └─ 别人占的 ─┘   └─ 我即将要用的净增量 ─┘
```

`+ current` 是因为 `used` 已经把 `current` 算进去了，而我们想用 `peak` 代替 `current` 来预留 —— 等价于 `total×0.9 − (used − current) − peak`：**扣掉非本进程占用，再扣掉本进程的峰值**。

这一步的隐含假设：**真实推理的峰值 ≈ warmup 的峰值**。warmup 用的是"最长、最宽"的一次前向（见下），所以这个假设在 batch ≤ 配置上限时成立；如果用户传 `max_num_batched_tokens` 很大但实际跑更宽的 batch，就会 OOM —— 因为 `max_num_batched_tokens` 就是用来定义"最宽"的。

`assert num_kvcache_blocks > 0` 是唯一的失败提示：显存不够时你只看到 `AssertionError`，看不到"差了多少"。

## 3. warmup：为什么必须先跑一次假 prefill

```python
# model_runner.py:91-101
def warmup_model(self):
    torch.cuda.empty_cache()
    torch.cuda.reset_peak_memory_stats()
    max_num_batched_tokens, max_model_len = self.config.max_num_batched_tokens, self.config.max_model_len
    seq_len = min(max_num_batched_tokens, max_model_len)
    num_seqs = min(max_num_batched_tokens // seq_len, self.config.max_num_seqs)
    seqs = [Sequence([0] * seq_len) for _ in range(num_seqs)]
    for seq in seqs:
        seq.num_scheduled_tokens = seq_len
    self.run(seqs, True)          # ← 一次真正的前向，只是数据全是 0
    torch.cuda.empty_cache()
```

默认配置下：`seq_len = min(16384, 4096) = 4096`，`num_seqs = min(16384//4096, 512) = 4` → **4 条 4096 token 的 prefill，共 16384 token**。这就是"峰值"的定义：它把 `max_num_batched_tokens` 一次吃满。

三个精妙处：

1. **内存池预热**：第一次前向会触发 CUDA 分配器向驱动申请大块内存。不预热的话，`peak` 只反映"建模型"的量，KV 池会算得过大，真实推理时 OOM。
2. **`torch.compile` 预热**：`RMSNorm`、`RoPE`、`Sampler`、`SiluAndMul` 都带 `@torch.compile`（`docs/11`）。第一次调用要编译（数百毫秒到数秒），warmup 把它吃掉，避免第一次真实请求超时。
3. **`block_table` 为空**：warmup 的 `Sequence` 从没经过 `allocate`，所以 `prepare_prefill` 里 `if not seq.block_table: continue`（`model_runner.py:149-150`）直接跳过 `slot_mapping`；而 `Attention.k_cache` 此时还是空 tensor（`attention.py:57`），`store_kvcache` 被 `if k_cache.numel()` 挡住（`attention.py:62`）。

**所以 warmup 是一个"不走 KV 的 prefill"** —— 它测量的是"算力与中间激活的峰值"，不含 KV。这恰好是想要的：KV 池要用的显存在公式里单独算（第 2 节）。

## 4. 分配与注入

```python
# model_runner.py:115-121
self.kv_cache = torch.empty(2, hf_config.num_hidden_layers, config.num_kvcache_blocks,
                            self.block_size, num_kv_heads, head_dim)
layer_id = 0
for module in self.model.modules():
    if hasattr(module, "k_cache") and hasattr(module, "v_cache"):
        module.k_cache = self.kv_cache[0, layer_id]
        module.v_cache = self.kv_cache[1, layer_id]
        layer_id += 1
```

- **`torch.empty` 不带 dtype**：沿用第 4 步 `torch.set_default_dtype(hf_config.dtype)` 设的 bf16。顺序不能换。
- **一整块大张量**，不是 28 个小张量：好处是一次分配、内存连续、`block_table` 的页号索引可以直接算偏移；坏处是不能单独释放某一层。
- **`kv_cache[0, layer_id]` 是视图，不是拷贝**：所以 28 个 `Attention` 模块共享同一块显存。

**隐式契约**：`self.model.modules()` 的遍历顺序必须与"层号顺序"一致。`nn.Module.modules()` 是深度优先、按注册顺序，而 `Qwen3Model` 用 `nn.ModuleList([...])` 顺序注册，所以成立。

但这个写法很脆：`hasattr(module, "k_cache")` 对每个 `Attention` 都成立（`attention.py:57` 初始化成空 tensor），一旦模型里加入了别的带 `k_cache` 属性的模块（比如未来加个 MLA 层、或者加个带缓存的视觉塔），`layer_id` 就会错位，**静默把错误的层接到错误的显存上** —— 不报错，只是精度崩。更稳的写法是按名字解析（`model.layers.{i}.self_attn`）。

## 5. 从块号到字节偏移（下一课的前置）

```
kv_cache[0]  # K, shape [num_layers, num_blocks, block_size, kv_heads, head_dim]
kv_cache[1]  # V, 同形状

第 layer 层：kv_cache[0, layer]  →  [num_blocks, 256, 8, 128]
第 block 块：  [block_id]        →  [256, 8, 128]
块内第 j 个：  [j]               →  [8, 128]

slot = block_id * block_size + j
```

`slot_mapping` 里存的就是这个 `slot`（`prepare_prefill` 里逐块拼出来，`model_runner.py:153-161`）。Triton kernel 拿 `slot` 直接算偏移（`attention.py:28`：`cache_offsets = slot * D + arange(D)`）。

注意 `k_cache.stride(1) == D` 这个断言（`attention.py:38`）：它要求 `block_size` 维连续，也就是"块内 256 个位置紧挨着"。这是 FlashAttention 的 paged 布局要求，`kv_cache` 一次性用 `torch.empty` 分配正好保证了连续性 —— 如果哪天改成"每块单独分配"，这个断言就会挂。

## 6. 拓扑图

```
GPU 显存
├── CUDA context + 驱动            （算进 used，被扣掉）
├── 模型权重（bf16，~1.2 GB / 0.6B）  （算进 peak）
├── 中间激活（warmup 峰值）           （算进 peak）
└── KV 池 num_kvcache_blocks × 28 MiB
     kv_cache: [2, 28, N, 256, 8, 128]
       ├── 视图 → layers[0].self_attn.k_cache / v_cache
       ├── 视图 → layers[1].self_attn.k_cache / v_cache
       └── ...
```

## 7. 陷阱清单

1. **`num_kvcache_blocks` 是构造时算死的**：跑起来以后显存变化（别的进程起来）不会再调，OOM 只能重启。
2. **warmup 的 `max_num_batched_tokens` 就是显存规划的上限**：设太大浪费 KV 池（因为预留给激活），设太小限制批次。
3. **`assert > 0` 没有诊断信息**：显存不够时无法知道差多少。想改的话把 `free/total/peak/current/block_bytes` 打进错误消息。
4. **注入依赖模块顺序**：加任何带 `k_cache` 属性的模块都会错位。
5. **TP 下 `num_kv_heads // world_size` 必须整除**：`num_key_value_heads=8` 最多 8 卡；`config.py:23` 的 `assert 1 <= tp <= 8` 不是巧合。
6. **块大小必须是 256 的倍数**（`config.py:22`）：因为 `block_size` 同时决定了 `Sequence.block_size`、slot 计算和 FlashAttention 页大小，改动会牵动 kernel 的对齐假设。
