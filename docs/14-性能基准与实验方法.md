## 1. `bench.py` 逐段

```python
# bench.py:8-28
def main():
    seed(0)
    num_seqs = 256
    max_input_len = 1024
    max_ouput_len = 1024                       # ← 原作者的拼写，不是我的笔误

    path = os.path.expanduser("~/huggingface/Qwen3-0.6B/")
    llm = LLM(path, enforce_eager=False, max_model_len=4096)

    prompt_token_ids = [[randint(0, 10000) for _ in range(randint(100, max_input_len))] for _ in range(num_seqs)]
    sampling_params = [SamplingParams(temperature=0.6, ignore_eos=True, max_tokens=randint(100, max_ouput_len)) for _ in range(num_seqs)]
    # uncomment the following line for vllm
    # prompt_token_ids = [dict(prompt_token_ids=p) for p in prompt_token_ids]

    llm.generate(["Benchmark: "], SamplingParams())      # ← 预热一次
    t = time.time()
    llm.generate(prompt_token_ids, sampling_params, use_tqdm=False)
    t = (time.time() - t)
    total_tokens = sum(sp.max_tokens for sp in sampling_params)
    throughput = total_tokens / t
    print(f"Total: {total_tokens}tok, Time: {t:.2f}s, Throughput: {throughput:.2f}tok/s")
```

六个变量的意图：

| 变量 | 值 | 为什么这么设 |
| --- | --- | --- |
| `seed(0)` | 固定 | 让两套引擎跑**同一批请求**（输入长度、输出长度逐个相同） |
| `num_seqs=256` | 256 | 足够压满批次，又不至于让 8 GB 卡 OOM |
| `max_input_len=1024` | 100–1024 随机 | 模拟长短混合；**上限 1024 = 4 个 256 块** |
| `max_ouput_len=1024` | 100–1024 随机 | 输出越长，平均每步 batch 越小（先完成的先退出） |
| `ignore_eos=True` | 开 | 保证每步都生成满 `max_tokens`，**否则总 token 数不可预测、无法横向对比** |
| `prompt_token_ids` 随机 | `randint(0,10000)` | 不用真实文本 → **没有前缀缓存收益**，纯测计算路径 |

最后一条是个容易被忽略的设计选择：用随机 token id 意味着**每条 prompt 都和别人的不同**，块哈希全不命中。所以这份基准测的是"冷启动吞吐"，含全部 prefill 计算，**不代表有 cache 命中的真实业务负载**。想测前缀缓存收益，得让多条 prompt 共享前缀。

`# uncomment the following line for vllm` 那一行说明：vLLM 的接口要 `dict(prompt_token_ids=...)` 包一层，其余代码完全一致。**这是作者做公平对比的关键 —— 同一份请求集、同一个模型、同一台机器，只换引擎。**

## 2. 预热那一行为什么必要

```python
llm.generate(["Benchmark: "], SamplingParams())
```

`LLM` 的构造里已经做了 warmup（`docs/08`，4×4096 token 的假 prefill）和 CUDA Graph 捕获（`docs/13`）。这一行额外做的事：

- 让 `torch.compile` 的**采样器**（`Sampler.forward`）编译好 —— 构造期的 warmup 只跑 prefill 分支，decode 走的是另一条 trace；
- 让 tqdm、tokenizer 的解码路径预热。

不预热的话，第一次 `generate` 会把编译时间算进总时间（对小模型可能高达 10–20%），对比就失真了。

## 3. README 那张表

```
**Test Configuration:**
- Hardware: RTX 4070 Laptop (8GB)
- Model: Qwen3-0.6B
- Total Requests: 256 sequences
- Input Length: Randomly sampled between 100–1024 tokens
- Output Length: Randomly sampled between 100–1024 tokens

| Inference Engine | Output Tokens | Time (s) | Throughput (tokens/s) |
| vLLM             | 133,966       | 98.37    | 1361.84               |
| Nano-vLLM        | 133,966       | 93.41    | 1434.13               |
```

先做一致性检查（我算的）：

```
133,966 / 256 = 523.3  token/请求      ← uniform[100,1024] 的期望是 562，固定 seed 下的实际抽样
133,966 / 93.41 = 1434.2 tok/s         ← 与表中 1434.13 一致
133,966 / 98.37 = 1361.8 tok/s         ← 与表中 1361.84 一致
```

三个数字互相吻合，说明这张表是同一份请求集的真实输出（不是估算）。nano-vllm 快 **5.3%**（98.37/93.41 = 1.053）。

### 能得出什么

- 在这台机器、这个模型、这批请求上，nano-vllm 的端到端吞吐不低于 vLLM；
- "1450 行代码能打平几万行的成熟引擎"这个结论**成立**（对单卡、小模型、无前缀复用、短上下文的场景）。

### 不能得出什么

| 不能说的 | 原因 |
| --- | --- |
| "nano-vllm 比 vLLM 快" | 5.3% 在单次测量里可能是噪声；没有重复次数、没有方差、没有 `p99` |
| "长上下文也一样快" | `max_model_len=4096`，而 nano-vllm 没有滑窗/稀疏注意力，长上下文会吃满 KV |
| "有前缀缓存的业务场景更快" | 请求是随机 token，**前缀缓存完全没命中** |
| "多卡也这样" | 单卡 TP=1，没有跨卡通信开销 |
| "在线服务吞吐" | 这是**离线批处理**吞吐；在线还要看 TTFT/ITL/尾延迟 |

**方法论上最重要的一条**：`Throughput = 总输出 token / 墙钟时间`，分母里**包含所有 prefill 时间**。所以这个数字衡量的是"一整个离线批次跑完的平均速度"，不是"用户感受到的生成速度"。要评估在线体验，必须另外测：

- **TTFT**（首 token 延迟）= 从提交到第一个 token，受 prefill 与排队影响；
- **ITL / TPOT**（token 间隔）= decode 步长，受 batch size 与 KV 长度影响；
- **尾延迟**（p95/p99）：受调度与抢占影响（`docs/06` 的饥饿问题会直接反映在这里）。

这三个指标 nano-vllm **一个都没有埋点**（`Sequence` 里没有时间戳），需要自己加。

## 4. 本机能做什么

| 实验 | 本机可行性 |
| --- | --- |
| 端到端 tok/s | ✗ 无 CUDA（Apple M5，`torch.cuda` 不可用） |
| 调度行为（饥饿/抢占/分块） | ✓ `labs/sim_scheduler.py`，纯 CPU 跑原码 |
| 前缀缓存命中率 | ✓ `labs/sim_prefix_cache.py`，可穷举不同 prompt 组合 |
| KV 显存公式/块字节数 | ✓ 纯算术（`docs/08`），可用脚本枚举配置 |
| CUDA Graph 收益 | ✗ 需要 GPU |
| kernel 效率 | ✗ 需要 GPU + Nsight |

**这个分界本身就是一个可迁移的方法**：任何推理引擎，**调度与缓存策略可以在 CPU 上做仿真验证，kernel 与图优化必须上真机**。前者是"逻辑正确性"，后者是"性能实现"。

## 5. 自己复现时的实验矩阵

按变量优先级排：

| 变量 | 建议取值 | 想回答的问题 |
| --- | --- | --- |
| `max_num_batched_tokens` | 512 / 2048 / 16384 | prefill 分块对吞吐与 TTFT 的影响 |
| `max_num_seqs` | 8 / 64 / 512 | 批次上限对 decode 吞吐的影响（以及 KV 是否够） |
| `kvcache_block_size` | 256（唯一可用） | 结构性参数，不改（`config.py:22` 断言） |
| `gpu_memory_utilization` | 0.7 / 0.9 | KV 池大小 ↔ 可并发长度 |
| `tensor_parallel_size` | 1 / 2 | 小模型 TP 的收益阈值（通信 vs 算力） |
| `enforce_eager` | True / False | CUDA Graph 的真实收益 |
| prompt 长度分布 | 128 / 1024 / 4096 | 前缀缓存与分块的影响 |
| 是否共享前缀 | 同前缀 vs 全随机 | 前缀缓存的收益上限 |

**一次只改一个**，并且固定 `seed(0)`。每个配置至少跑 3 次取中位数 —— `bench.py` 只跑一次，这是它最大的方法论弱点。

## 6. 一个可复现的对照实验设计（写论文/汇报用）

```
目标：量化 nano-vllm 相对 vLLM 的差距来自哪里

对照 1（同配置）：两引擎都用 CUDA Graph、TP=1、max_num_seqs=512、随机 prompt
对照 2（关图）：nano-vllm enforce_eager=True vs False → 图收益
对照 3（共享前缀）：50% 的 prompt 共享 512 token 前缀 → 前缀缓存收益
对照 4（长输出）：max_tokens=2048 → 调度与抢占的影响
对照 5（并发放大）：num_seqs=1024、max_model_len=4096 → KV 压力与弃单

每个对照记录：吞吐、TTFT(p50/p99)、ITL(p50/p99)、显存峰值、抢占次数
（后两项需要自己埋点：抢占次数在 scheduler.py:76 加一个计数器）
```

这个设计能直接回答"nano-vllm 为什么能打平 vLLM"：如果对照 1 打平、对照 2 差距大，说明**赢在"省略"而不是"更聪明"** —— 它省掉了服务端、调度复杂度、指标埋点，把这些成本还给了吞吐。

## 7. 陷阱

1. **只跑一次就下结论**：`bench.py` 单次测量，±5% 完全可能是噪声。
2. **吞吐定义混用**：把 `total_tokens/时间` 当"生成速度"报出去（它含 prefill 和排队）。
3. **`ignore_eos` 忘了开**：总 token 数不可控，两套引擎不可比。
4. **随机 prompt 当"真实负载"**：真实业务的重复前缀、变长分布、结束位置都不同。
5. **换机器对比**：README 的 4070 Laptop 数字不能和你 4090 的结果放一张表。
