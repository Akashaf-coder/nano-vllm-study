# 02 请求生命周期：七个阶段

## 本课目标

- 跟着一条 prompt 从 `generate` 走到 token，每一跳都有 `文件:行号`；
- 弄清 `step()` 的返回值为什么要用**负数**编码 decode；
- 知道第一个输出 token 是哪一步产生的（答案是：prefill 那一步）。

## 1. 七个阶段

| # | 阶段 | 代码位置 | 产物 |
| --- | --- | --- | --- |
| 1 | 参数归一 + 建进度条 | `llm_engine.py:66-68` | `sampling_params` 列表 |
| 2 | 分词 | `llm_engine.py:44-45` | `list[int]` |
| 3 | 建请求 | `llm_engine.py:46` | `Sequence` 进 waiting |
| 4 | 调度 | `scheduler.py:25-73` | `(seqs, is_prefill)` |
| 5 | GPU 前向 | `model_runner.py:214-220` | `token_ids`（每条一个） |
| 6 | 后处理 | `scheduler.py:81-92` | 状态推进 / 结束判定 / 释放块 |
| 7 | 收集 + 解码 | `llm_engine.py:54-55, 84-89` | `[{"text", "token_ids"}]` |

## 2. 阶段 3：入队

```python
# llm_engine.py:43-47
def add_request(self, prompt: str | list[int], sampling_params: SamplingParams):
    if isinstance(prompt, str):
        prompt = self.tokenizer.encode(prompt)
    seq = Sequence(prompt, sampling_params)
    self.scheduler.add(seq)
```

注意 `tokenizer.encode(prompt)` **不加 chat template**。`example.py:17-23` 里是用户自己 `apply_chat_template(...)` 之后再传进来的 —— 引擎不管对话格式。这是"最小实现"的直接后果，也是新手最容易踩的坑：直接传 `"你好"` 得到的是 base 模型行为。

## 3. 阶段 4-6：一次 step

```python
# llm_engine.py:49-55
def step(self):
    seqs, is_prefill = self.scheduler.schedule()
    num_tokens = sum(seq.num_scheduled_tokens for seq in seqs) if is_prefill else -len(seqs)
    token_ids = self.model_runner.call("run", seqs, is_prefill)
    self.scheduler.postprocess(seqs, token_ids, is_prefill)
    outputs = [(seq.seq_id, seq.completion_token_ids) for seq in seqs if seq.is_finished]
    return outputs, num_tokens
```

**`num_tokens` 用符号编码两种语义**：prefill 时是"这一步算了多少个 prompt token"，decode 时是"这一步有 -N 条序列各出 1 token"（负数）。`generate` 靠这个符号分流两条吞吐统计：

```python
# llm_engine.py:76-79
if num_tokens > 0:
    prefill_throughput = num_tokens / (perf_counter() - t)
else:
    decode_throughput = -num_tokens / (perf_counter() - t)
```

这两行就是 tqdm 上 `Prefill: 12ktok/s  Decode: 450tok/s` 的来源。**它统计的是"引擎侧吞吐"，不是"用户感知延迟"** —— 没有 TTFT/ITL 指标，因为那需要请求级时间戳，`Sequence` 里没有这个字段（`sequence.py:19-31` 只有 token 计数）。

## 4. 阶段 5：ModelRunner.run 内部（真正的六步）

```python
# model_runner.py:214-220
def run(self, seqs, is_prefill) -> list[int]:
    input_ids, positions = self.prepare_prefill(seqs) if is_prefill else self.prepare_decode(seqs)
    temperatures = self.prepare_sample(seqs) if self.rank == 0 else None
    logits = self.run_model(input_ids, positions, is_prefill)
    token_ids = self.sampler(logits, temperatures).tolist() if self.rank == 0 else None
    reset_context()
    return token_ids
```

五个细节，每个都值一节课：

1. `prepare_prefill` / `prepare_decode` 除了造 `input_ids`，还负责**把上下文塞进全局单例**（`utils/context.py`）—— 注意力层没有参数传递，全靠 `get_context()` 取 `slot_mapping`、`block_tables`。这是全项目最"不显式"的设计（`docs/09`）。
2. 只有 `rank == 0` 准备温度和采样，其他 rank 返回 `None` —— 采样只在主卡做（`docs/07`）。
3. `run_model` 内部还有一次分流：prefill、`enforce_eager`、或 batch>512 走**直接前向**，否则走 **CUDA Graph 重放**（`model_runner.py:197-212`，`docs/13`）。
4. `compute_logits` 只对每条序列的最后一个位置算（`docs/11`），所以 prefill 的 logits 形状是 `[bs, vocab]` 而不是 `[总token数, vocab]`。
5. `reset_context()` 在返回前清空全局上下文 —— 这是防"脏指针"的手动 close，漏了会读到上一批的 `slot_mapping`。

## 5. 阶段 6：postprocess 的四个动作

```python
# scheduler.py:81-92
def postprocess(self, seqs, token_ids, is_prefill):
    for seq, token_id in zip(seqs, token_ids):
        self.block_manager.hash_blocks(seq)          # ① 给已写满的块打哈希
        seq.num_cached_tokens += seq.num_scheduled_tokens   # ② 推进缓存计数
        seq.num_scheduled_tokens = 0
        if is_prefill and seq.num_cached_tokens < seq.num_tokens:
            continue                                 # ③ 分块预填还没完，不生 token
        seq.append_token(token_id)                   # ④ 追加 token
        if (not seq.ignore_eos and token_id == self.eos) or seq.num_completion_tokens == seq.max_tokens:
            seq.status = SequenceStatus.FINISHED
            self.block_manager.deallocate(seq)
            self.running.remove(seq)
```

**③ 是关键**：分块预填的第一块、第二块都不会产生 token，只有 `num_cached_tokens == num_tokens`（最后一块）才 `append_token`。**所以"第一个输出 token 是在 prefill 那一步产出的"** —— 不是先 prefill 完再单独一步 decode。`labs/sim_scheduler.py` case1 的实测能看见：

```
step3: PREFILL(6tok)  waiting=1 running=1 | #0:running 30/31
                                              ↑ 预填完 30 token，立刻 append 到 31
```

这对基准测试的意义：`max_tokens=256` 时实际前向步数是 1 次 prefill + 255 次 decode，不是 256 次 decode。

## 6. 阶段 7：generate 的主循环

```python
# llm_engine.py:73-89
while not self.is_finished():
    t = perf_counter()
    output, num_tokens = self.step()
    ...
    for seq_id, token_ids in output:
        outputs[seq_id] = token_ids
        pbar.update(1)
...
outputs = [outputs[seq_id] for seq_id in sorted(outputs.keys())]
outputs = [{"text": self.tokenizer.decode(token_ids), "token_ids": token_ids} for token_ids in outputs]
```

两个实现细节：

- **按 `seq_id` 排序回填**：`Sequence.counter` 是全局自增（`sequence.py:16`），完成顺序与提交顺序无关，所以最后必须按 id 重排才能对应用户传入的 prompts 顺序。
- **`is_finished()` 是"两个队列都空"**（`scheduler.py:19-20`），不是"已提交的都完成" —— 因为没有取消机制，两者的差别在有异常的路径上才体现。

## 9. 陷阱

1. **以为 prompt 是流式进来的**：`generate` 先把所有 prompt 一次性入队，中间无法插入新请求 —— 真正的连续批处理要等 vLLM V1 那种"每步都从队列取新的"。
2. **以为 prefill 和 decode 会同批**：不会，`schedule()` 先看 waiting，能调度就 `return`（`scheduler.py:54-55`），根本没机会 mix。
3. **以为 `num_tokens` 是 token 数**：decode 时它是负数，直接除时间会得到负吞吐。
4. **以为 `max_tokens` 是总长度**：是生成长度（`num_completion_tokens`），prompt 长度不计入。
