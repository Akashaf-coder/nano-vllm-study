# 06 抢占与重算

## 本课目标

- 抢占在这份代码里到底做了什么（四行，三个副作用）；
- 为什么"抢占 = 全量重算"而不是"从断点续算"，代价有多大；
- LIFO 选择受害者的后果，以及本机实测到的"救不了自己"的边界；
- 三种改法（swap / 优先级 / 准入限制）各要动哪里。

## 1. 抢占只有四行

```python
# scheduler.py:75-79
def preempt(self, seq: Sequence):
    seq.status = SequenceStatus.WAITING
    seq.is_prefill = True
    self.block_manager.deallocate(seq)     # ← 关键：KV 全丢
    self.waiting.appendleft(seq)
```

副作用一：`deallocate` 把 `num_cached_tokens` 归零、`block_table` 清空。

```python
# block_manager.py:94-101
def deallocate(self, seq):
    for block_id in reversed(seq.block_table):     # ① 逆序释放
        block = self.blocks[block_id]
        block.ref_count -= 1
        if block.ref_count == 0:
            self._deallocate_block(block_id)
    seq.num_cached_tokens = 0                      # ② 缓存进度清零
    seq.block_table.clear()                        # ③ 映射清空
```

副作用二：`appendleft` —— 被抢占的序列**排到 waiting 最前面**，下次调度优先它。这是唯一一点"补偿"。

副作用三：`token_ids` **保留**。所以重算时能重新 prefill 整段（prompt + 已生成的 token），文本不丢。`num_prompt_tokens` 也不变，于是"重算的 prefill 长度"是 `num_tokens` 而不是原始 prompt 长度 —— **生成得越久，被抢占越亏**。

## 2. 三种触发路径

```
① 正常增长：decode 时 can_append 为假
   scheduler.py:60-65
   while not can_append(seq):
       if self.running: preempt(self.running.pop())   → 抢队尾
       else:            preempt(seq); break           → 抢自己

② 队首准入失败（不是抢占，是阻塞）
   scheduler.py:36-38  can_allocate == -1 → break     → 整批停等，没人被抢

③ 块耗尽的根因
   num_kvcache_blocks 由显存算出（docs/08），没有为"突发长序列"预留水位
```

注意 ① 和 ② 的区别：**decode 阶段是"抢别人保自己"，prefill 阶段是"都别动，等"。** 这两种策略混在一个调度器里，是它行为难以预测的主要原因。

## 3. 为什么只能全量重算

`deallocate` 之后块内容虽然还在物理内存里（没被清零），但：

1. `block_table` 清空 → 不知道该读哪些块；
2. `num_cached_tokens = 0` → `prepare_prefill` 的 `start` 变成 0，从头算；
3. 重新 `allocate` 时会走 `can_allocate` —— **只有那些块的哈希还在索引里，才可能命中**。而 `_deallocate_block` 只把块放回 free，索引不删，所以：

```
被抢占的序列重新 prefill：
  自己的块 ← 可能还在 free 里、索引还在 → 部分命中（运气好）
  自己的块 ← 已被别的序列申请走 → 索引被 _allocate_block 清掉 → 全量重算
```

**所以"重算"其实是"尽可能再命中一次前缀缓存"**，最优情况是自己占的块没被抢走，能省下一些 prefill；最坏情况是全量。这也解释了为什么 `appendleft`（插队）很重要：越早回来，块越可能还在。

## 4. 代价估算

重算一条 `L` token 序列的成本 ≈ 一次长度 `L` 的 prefill。用 `docs/14` 里 README 的数字做个数量级感受（RTX 4070 Laptop，Qwen3-0.6B，prefill 吞吐按 1 万 tok/s 粗估）：

| 被抢占序列长度 | 重算耗时 | 期间其它序列 |
| ---: | ---: | --- |
| 512 | ~0.05 s | 正常 decode |
| 2048 | ~0.2 s | 正常 decode |
| 4096 | ~0.4 s | 正常 decode（但本步的 prefill 会抢占配额） |

对比"swap 到 CPU 再换回"：4096 token × 28 层 × 2 × 8 头 × 128 维 × 2 字节 ≈ 28 MiB/块 × 16 块 ≈ 448 MiB —— 换出换回要搬 448 MiB，PCIe 4.0 x16 理论 32 GB/s，实测约 20 GB/s，来回 ≈ 45 ms。**在小模型 + 短上下文时，重算（0.4 s）比重算便宜但比 swap 贵；在长序列上 swap 更划算。** 这就是 vLLM 保留 swap 的原因，也是 nano-vllm 敢砍掉它的原因：目标场景是小模型、短上下文、离线批处理。

（上面的 prefill 吞吐与 PCIe 带宽都是**估算**，不是本项目实测；`docs/14` 会说明 README 只给了端到端吞吐。）

## 5. 本机实测：LIFO 与饥饿

`labs/sim_scheduler.py` case3（4 个块、`block_size=4`、两条 8 token 序列）：

```
[prefill 完] waiting=0 running=2 | #0:running 8/9  #1:running 8/9
step0: DECODE(bs=1)  waiting=1 running=1 | #1:waiting 0/9  #0:running 9/10
step1: DECODE(bs=1)  waiting=1 running=1 | #1:waiting 0/9  #0:running 10/11
step2: DECODE(bs=1)  waiting=1 running=1 | #1:waiting 0/9  #0:running 11/12
step3: DECODE(bs=1)  waiting=1 running=1 | #1:waiting 0/9  #0:running 12/13
```

读法：

- **`running.pop()` 是队尾**，所以受害的是最后进入 running 的 B。这就是 LIFO。
- B 回到 waiting 后 `num_cached_tokens=0`（`0/9`），但**它一直没回来**：A 每 3 步就吃掉一个新块，free 始终不足以让 B 重新 `allocate`（B 需要 2 块）。
- 也就是说：**"抢占"在本配置下不是"暂停"，而是"无限期推迟"**。没有 swap、没有优先级、没有配额预留，被抢的序列只能等 A 结束。

这个现象在真实负载里的对应物是：长序列把短序列挤出去，短序列排队到长序列全部结束 —— **没有公平性**。

## 6. 边界：抢占救不了自己的时候会崩

`labs/sim_scheduler.py` case5（`num_kvcache_blocks=2`，单条 8 token 序列占满）：

```
预填：PREFILL(8tok)，free_blocks=0，len(seq)=9
确认：AssertionError 从 scheduler.py:71 抛出。
```

代码路径：

```python
while not self.block_manager.can_append(seq):
    if self.running:                 # running 已经空了（只有自己）
        self.preempt(self.running.pop())
    else:
        self.preempt(seq)            # 抢自己：块被释放了……
        break                        # ……但 break 跳过了下面的 else 分支
else:                                # while-else：只有"没 break"才执行
    ...
assert scheduled_seqs                # 空 → 崩
```

**注意 `while ... else` 的语义**：`else` 属于 `while`，只在循环正常结束（条件变假）时执行。`break` 直接跳过它，所以"抢自己"这条路径永远不会被调度。逻辑上应该 `continue` 重试（此时块已释放，`can_append` 会变真），但代码选择了 `break`。

这是一个真实的边界缺陷（无消息的 `AssertionError`），触发条件是"某条序列自己就需要超过全部 KV 池的块"。默认配置下 `num_kvcache_blocks` 由显存自动算（通常几千块），只有人为设小或极小显存才会撞到。

## 7. 三种改法

### 改法 A：swap 到 CPU（对齐 vLLM）

在 `preempt` 里不要 `deallocate`，而是把 `seq.block_table` 对应的 KV 拷到 pinned CPU 张量，记录映射；回来时拷回。要改：`block_manager` 增加 swap 空间管理、`ModelRunner` 增加两条拷贝指令、`scheduler` 增加 `swapped` 队列。**大约 100–150 行**，是"能不能改成生产可用"的分水岭。

### 改法 B：只管准入，不抢占

`add_request` 时检查 `seq.num_blocks <= num_kvcache_blocks`，超了直接拒绝/排队。**改动 1 行**，代价是长请求永远进不来（但对 demo 来说足够）。

### 改法 C：给抢占加"代价上限"

如果重算成本 > 某个阈值（比如序列长度 × 层数），就宁可 `break` 让整批等等，或抢最年轻的而不是最后一个。要改 `scheduler.py:60-65` 的选择逻辑，约 20 行。这是最贴近"生产调度策略"的改动。

## 8. 与 DeepInfer 的思路对照（详见 docs/15）

DeepInfer 面对同一问题的解法完全不同：它**不允许无限重算**，而是把重算量硬编码上界 —— YoCo 的 bounded replay 只重算 128 token + 6 层（外部资料），配合 ZOS 把 CPU 调度藏进 GPU 执行窗口。

两种哲学的差别：

| | nano-vllm | DeepInfer |
| --- | --- | --- |
| 显存不够 | 清空重算，量无上界 | 受限重算，量有上界 |
| 调度 | 同步、批级、CPU 在关键路径上 | 异步、CPU 藏在 GPU 后面 |
| 目标 | 教学可读 | 生产吞吐 |
