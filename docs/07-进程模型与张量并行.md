# 07 进程模型与张量并行

## 本课目标

- 画出 rank0（主进程）与 rank1..N-1（子进程）的控制流差异；
- 看懂 SharedMemory + Event 这套 IPC 为什么够用、什么时候不够；
- 知道 `call()` 的分发规则、采样为什么只在 rank0；
- 记住四个会咬人的硬编码（端口、shm 名、1MB 上限、设备号 == rank）。

## 1. 进程布局

```python
# llm_engine.py:22-31
self.ps = []; self.events = []
ctx = mp.get_context("spawn")
for i in range(1, config.tensor_parallel_size):
    event = ctx.Event()
    process = ctx.Process(target=ModelRunner, args=(config, i, event))
    process.start()
    self.ps.append(process); self.events.append(event)
self.model_runner = ModelRunner(config, 0, self.events)    # ← rank0 在当前进程
```

三个要点：

1. **`spawn` 而非 `fork`**：子进程重新 import 一遍，不继承 CUDA context —— 这是多卡场景唯一安全的启动方式（`fork` + CUDA 会挂）。
2. **rank0 不另起进程**：它在调用者进程里。所以 `LLM.generate` 是**同步阻塞**的 —— 主进程被前向计算占满，没有独立的前端线程。
3. **`args=(config, i, event)`**：子进程的入口就是 `ModelRunner.__init__` 本身，构造完不会返回（末尾调 `loop()` 阻塞）。

```python
# model_runner.py:41-48
if self.world_size > 1:
    if rank == 0:
        self.shm = SharedMemory(name="nanovllm", create=True, size=2**20)
        dist.barrier()
    else:
        dist.barrier()
        self.shm = SharedMemory(name="nanovllm")
        self.loop()          # ← 子进程永久阻塞在这里
```

rank0 创建共享内存并用 `dist.barrier()` 保证子进程能打开；子进程随后进入 `loop()` 等指令。

## 2. 通信协议：4 字节长度 + pickle

```python
# model_runner.py:68-83
def read_shm(self):
    self.event.wait()
    n = int.from_bytes(self.shm.buf[0:4], "little")
    method_name, *args = pickle.loads(self.shm.buf[4:n+4])
    self.event.clear()
    return method_name, args

def write_shm(self, method_name, *args):
    data = pickle.dumps([method_name, *args])
    n = len(data)
    self.shm.buf[0:4] = n.to_bytes(4, "little")
    self.shm.buf[4:n+4] = data
    for event in self.event:
        event.set()
```

协议极简：`[4 字节长度][pickle 数据]`。同步靠 `multiprocessing.Event`（每个子进程一个，由 rank0 持有列表 `self.events`）。

调用分发：

```python
# model_runner.py:85-89
def call(self, method_name, *args):
    if self.world_size > 1 and self.rank == 0:
        self.write_shm(method_name, *args)        # 先广播
    method = getattr(self, method_name, None)     # 再本地执行（rank0 也跑同一份代码）
    return method(*args)
```

**这是"SPMD + 单一入口"的写法**：所有 rank 执行同一行代码，只是 rank0 多了一步"发指令"。没有 master/worker 的角色分支（除了 `loop()` 和采样）。

为什么不用 `dist.broadcast_object_list`？那需要 NCCL 参与集合通信，会和真正的前向 kernel 抢同一批流；用 shm + Event 让"传参"和"算"完全解耦，也顺便绕开了 NCCL 对大对象的低效。代价是**1MB 硬上限**（`size=2**20`）。

## 3. 1MB 上限意味着什么

`pickle.dumps([method_name, *args])` 里的 args 主要是 `seqs`（`Sequence` 列表）和 `is_prefill`。`Sequence.__getstate__`（`docs/03`）已经把 decode 阶段的体积压到 O(1)/条，但 **prefill 阶段要传完整 `token_ids`**：

| 场景 | 每条序列字节数（粗算） | 512 条 | 超 1MB？ |
| --- | ---: | ---: | --- |
| decode（只传 last_token） | ~200 B | ~100 KB | 否 |
| prefill 512 token | ~200 B + 512×4 B ≈ 2.2 KB | ~1.1 MB | **是** |

也就是：**TP > 1 且 prefill 批次很大时，`shm.buf[4:n+4] = data` 会静默截断**（numpy 风格 bufslice 赋值超出长度会抛 `ValueError` 或截断，取决于实现）。这不是理论问题：`max_num_batched_tokens` 默认 16384，一次 prefill 4 条 4096 token 的 prompt 就会超。

**结论**：nano-vllm 的 TP 在"短 prompt、小 batch"下才安全。想用得稳，要么调小 `max_num_batched_tokens`，要么改共享内存尺寸/换 `dist.broadcast_object_list`。这是读这份代码最实用的一个发现。

（我无法在本机实测这条 —— 需要 CUDA 才能构造 `ModelRunner`。上面是按 `pickle` 体积与字段做的推算，标注为**推算**，不是实测。）

## 4. ModelRunner 的构造顺序（十步，顺序不能换）

```python
# model_runner.py:17-39（顺序即依赖）
1  dist.init_process_group("nccl", "tcp://localhost:2333", ...)   # ← 端口写死
2  torch.cuda.set_device(rank)                                     # ← 设备号 == rank
3  记住默认 dtype，切到 hf_config.dtype（bf16）
4  torch.set_default_device("cuda")                                # ← 之后所有 tensor 默认上 GPU
5  self.model = Qwen3ForCausalLM(hf_config)                        # 在 GPU 上建参数
6  load_model(self.model, config.model)                            # safetensors → 参数分片
7  self.sampler = Sampler()
8  self.warmup_model()                                             # 跑一次满长 prefill 测峰值显存
9  self.allocate_kv_cache()                                        # 按剩余显存切 KV 块
10 if not enforce_eager: self.capture_cudagraph()                  # 捕获 decode 图
   然后恢复默认 device/dtype 回 cpu
```

第 4 步很关键：`torch.set_default_device("cuda")` 让后面 `Qwen3ForCausalLM(...)` 里的 `nn.Parameter(torch.empty(...))` 直接落在 GPU 上，省掉 `.cuda()`。代价是**这段代码不能在任何非 CUDA 环境 import 执行** —— 也是本机能读不能跑的原因之一。

第 8 步（warmup）为什么必须在第 9 步之前：见 `docs/08`。

## 5. 采样为什么只在 rank0

```python
# model_runner.py:214-220
temperatures = self.prepare_sample(seqs) if self.rank == 0 else None
logits = self.run_model(input_ids, positions, is_prefill)
token_ids = self.sampler(logits, temperatures).tolist() if self.rank == 0 else None
reset_context()
return token_ids
```

两层配合：

- 行并行层（`o_proj`、`down_proj`）末尾 `dist.all_reduce`（`linear.py:155`），**每个 rank 的 hidden_states 都是完整的**；
- 但 `lm_head` 是词表并行的：`ParallelLMHead.forward` 里 `dist.gather(logits, all_logits, 0)` 把各 rank 的分片 logits 收集到 rank0（`embed_head.py:62-65`）。

所以 rank0 拿到完整 `[bs, vocab]`，采样一次；其他 rank 返回 `None`。**采样器不需要跨卡同步**，这是"只 TP 不做 PP"带来的简化。

## 6. 退出流程

```python
# model_runner.py:50-59
def exit(self):
    if self.world_size > 1:
        self.shm.close(); dist.barrier()
        if self.rank == 0: self.shm.unlink()
    if not self.enforce_eager:
        del self.graphs, self.graph_pool
    torch.cuda.synchronize()
    dist.destroy_process_group()
```

```python
# llm_engine.py:35-41
atexit.register(self.exit)
def exit(self):
    self.model_runner.call("exit")    # ← 广播 "exit" 指令，子进程 loop() 收到后 break
    del self.model_runner
    for p in self.ps: p.join()
```

顺序值得注意：`call("exit")` 会先把 `exit` 写进 shm（子进程读到后跳出 `loop()`），然后 rank0 自己执行 `exit()`。`shm.unlink()` 由 rank0 做 —— **如果进程被 SIGKILL，unlink 不会发生，下次启动 `SharedMemory(create=True)` 会抛 `FileExistsError`**。

## 7. 四个硬编码坑

| 硬编码 | 位置 | 后果 |
| --- | --- | --- |
| `tcp://localhost:2333` | `model_runner.py:26` | 同机多实例、残留进程占端口 → `dist.init_process_group` 超时 |
| `SharedMemory(name="nanovllm")` | `model_runner.py:43,47` | 上次异常退出残留 → `FileExistsError`；多实例直接冲突 |
| `size=2**20` | `model_runner.py:43` | 大 batch prefill 的 pickle 超限（第 3 节） |
| `torch.cuda.set_device(rank)` | `model_runner.py:27` | 要求"逻辑 rank == 物理卡号"，`CUDA_VISIBLE_DEVICES` 顺序被改过就会错位 |

四条都是"最小实现"的自觉取舍，但在多实例/容器环境下会集中爆发。想改的话，第 1、2 条各加一个 `--master-port` / `shm_name` 参数即可。

## 8. 单卡时发生了什么

`tensor_parallel_size=1`（`example.py:9` 的默认）：

- `for i in range(1, 1)` 不执行 → 没有子进程、没有 Event；
- `ModelRunner(config, 0, self.events=[])`：`world_size == 1`，跳过 shm 分支，**不进 `loop()`**；
- `call()` 里 `world_size > 1` 为假 → 直接 `getattr` 本地执行。

所以单卡路径是"一个进程，一套代码"，没有任何 IPC 开销。`docs/02` 里那条 `call("run", ...)` 在单卡下就是普通函数调用 —— **这是读代码时最容易迷路的地方：`call` 看起来像 RPC，单卡下其实是直调。**

## 9. 时序图（TP=2）

```
主进程 (rank0)                     子进程 (rank1)
   │                                  │
   │  ModelRunner.__init__            │  ModelRunner.__init__
   │   init_process_group ◀── NCCL ──▶│   init_process_group
   │   shm create                     │   shm open
   │   warmup / kv / cudagraph        │   warmup / kv / cudagraph
   │                                  │   loop()  ── 阻塞等 Event
   │                                  │
   │  step():                         │
   │   call("run", seqs, is_prefill)  │
   │    write_shm(...) ── Event.set ─▶│  read_shm() → call("run", ...)
   │    getattr("run")(seqs, ...)     │  getattr("run")(seqs, ...)
   │      prepare_prefill/decode      │   （同一份代码）
   │      model forward ─── NCCL all_reduce / gather ───  model forward
   │      sampler (只 rank0)          │   返回 None
   │  ◀───────────────────────────────│
   │  postprocess（只在主进程）        │
```
